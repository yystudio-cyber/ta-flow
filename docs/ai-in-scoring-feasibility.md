# 评分模型引入 AI 的可行性与成熟方案调研

调研人：Claude（亲自执行）｜日期：2026-07-30
约束前提：**TA 平台要分发安装到每个 TA 的本地电脑运行**（单机、非服务端），因此所有方案
都必须回答"在别人的笔记本上还成立吗"。

---

## 零、结论摘要（先看这段）

1. **架构上已经预留了接口，接 AI 不需要大改。** 评分引擎里有 `setSemanticProvider(p)`
   （`src/shared/scoring-universal.js:214`，已导出 `:1598`），语义匹配是引擎设计之初就留的
   第三层（L3）。接入 AI 的最小形态就是给它一个更强的 provider。

2. **但在接 AI 之前，必须先修一个已经存在的严重不同步**：这个 provider **插件接了、平台没接**。
   实测同一份简历 + 同一个岗位 + 同一份引擎代码：

   | 候选人 | 人工分 | 平台侧（未接语义） | 插件侧（已接语义） | 差 |
   |---|---|---|---|---|
   | A｜金融风控引擎 | 80 | 79 | **93** | +14 |
   | B｜电商推荐引擎 | 60 | 87 | **90** | +3 |

   证据：`extension/boss-match-score/content.bundle.js:1905` 有
   `TA_ENGINE.setSemanticProvider(_sem)`；`src/main/services/scoring.ts` 全文无 semantic 字样。
   **这是比"数据源不同"更根本的不同步——连算法路径都不一样。** 如果现在接入 AI 语义能力
   而只接一边，差距只会更大。

3. **推荐路线：本地 embedding 模型（零数据外传）+ 云 API 只处理不含候选人信息的任务。**
   本地 embedding 正好解决评分模型现在最大的短板（"金融风控引擎"与"电商推荐引擎"
   字面像、实质不同），且完全不触碰数据出境问题。

4. **不建议把候选人简历送任何云 API**：境外 API 构成数据出境，需安全评估或备案，
   违规最高罚 500 万元并可责令停业；境内 API 的数据政策参差（DeepSeek 开放平台条款对
   "是否用于训练"保持沉默）。而"零数据保留（ZDR）"只在协商过的企业协议里提供，
   不在标准按量付费计划内。

5. **本地小模型做"结构化抽取"目前不可靠**，别指望它替代 JD 结构化：3-4B 模型的
   JSON 可解析率约 80.9%，8B 约 82.6%，14B 才到 90.3%；当 schema 带定义时，
   小模型的不合规率从 2-3% 飙到 68-69%。

## 一、现状实测（本调研的事实基线）

| 项 | 实测结果 | 证据 |
|---|---|---|
| 平台现有 AI 集成 | **零** | grep `openai/anthropic/llm/大模型/qwen/deepseek/api_key` 全库无实质命中 |
| 主进程对外网络出口 | **无** | 唯一 HTTP 服务是 jd-bridge，只 listen 127.0.0.1 |
| 引擎语义接口 | **已预留但只有插件接了** | `scoring-universal.js:214`；`content.bundle.js:1905` vs `scoring.ts` 无 |
| 插件 vs 平台分差（语义路径） | **最大 14 分** | 见结论 2 表格 |
| 插件 vs 平台分差（数据源） | **11 分**（A：平台 79 / 插件卡片层 68） | 插件只能读已渲染 DOM，RPA 能读卡片 Vue 状态 |
| 现有语义 provider 实现 | 同义词表 + TF-IDF（`parts/20-semantic.js`，纯字面） | 覆盖 IT 通用词，**没有汽车/感知领域词**（正是本次评分翻车的领域） |

> 两个不同步来源是**叠加**的：算法路径差 14 分、数据源差 11 分，真实场景下差距可能更大。

## 二、三条技术路线对比

### 路线 A：本地 embedding 模型（✅ 推荐，优先做）

**做什么**：把 `setSemanticProvider` 换成基于向量相似度的实现，让引擎能判断
"接口测试"与"支付风控"的语义距离，而不只是数字符是否相同。

| 维度 | 数据 |
|---|---|
| 技术栈 | `@huggingface/transformers`（Transformers.js）+ `onnxruntime-node`，纯 Node，Electron 原生支持 |
| 模型体积 | bge-small-zh 约 **100MB**；all-MiniLM-L6-v2 量化后约 **23MB**；bge-m3（多语言全功能）需 **2.46GB 内存**、1024 维 |
| 硬件要求 | CPU 可跑，无需 GPU。4-bit 量化模型在普通笔记本上可用 |
| 数据流向 | **完全本地，零外传** |
| 合规 | 无数据出境问题，不触发个保法跨境条款 |
| 效果依据 | 多语言 embedding 的余弦相似度在简历-岗位匹配上显著优于 TF-IDF 与预训练 BERT 基线；Resume2Vec 在 nDCG/RBO 上明显优于传统 ATS，技术类岗位提升尤其明显 |

**为什么这条最适合本项目**：
- 它解决的正是评分模型现在最痛的问题（域/语义混淆），而不是锦上添花；
- 引擎接口已经存在，改动集中在一处；
- 分发到 TA 本地时，模型文件可以随安装包走或首次启动下载一次，之后离线可用；
- 不需要任何 API key，不需要任何合规审批。

**工程注意**：
- Electron 打包 `onnxruntime-node` 需处理原生模块（`.node` 二进制）与 `asarUnpack`；
- **必须两边都接**（平台侧 `scoring.ts` + 插件侧），否则会把现有 14 分的不同步扩大；
- 插件在浏览器扩展环境里跑 ONNX 有额外约束（扩展 CSP、体积、`wasm`），
  可能需要改成"平台侧算好向量、经 17385 桥下发给插件"的形态——这一点需要设计时确认。

### 路线 B：本地生成式小模型（⚠️ 现阶段不推荐）

**做什么**：本地跑 3B-7B 模型做 JD 结构化、简历抽取。

| 维度 | 数据 |
|---|---|
| 技术栈 | `node-llama-cpp`（对 Electron 友好）或 Ollama（需用户另装） |
| 模型体积 | 7B 4-bit 量化约 4GB |
| 结构化输出可靠性 | 3-4B：**80.9%**；8B：82.6%；14B：90.3%。带 schema 定义时小模型不合规率 **68-69%** |
| 速度 | CPU 可跑但慢；长文档（简历）尤其吃力 |
| 分发问题 | 4GB 模型随安装包分发不现实；让每个 TA 自己装 Ollama 不可行 |

**结论**：能力不够 + 分发不现实。除非将来做微调（研究显示微调后 1B 模型能到 88.9% schema
准确率），否则这条路现在不成立。

### 路线 C：云 API（⚠️ 仅限不含候选人信息的任务）

| 风险项 | 事实 |
|---|---|
| 境外 API（OpenAI/Anthropic/Azure） | 调用即构成**数据出境**。依据《网络安全法》37 条、《数据安全法》31 条、《个人信息保护法》38 条，需通过安全评估或完成备案。违规可警告、没收违法所得、**罚款最高 500 万元**，情节严重可责令停业 |
| 零数据保留（ZDR） | OpenAI/Anthropic/Azure 都提供，但**只在协商过的企业协议里**，标准按量付费计划拿不到。Azure 的"修改版滥用监控"需单独申请审批 |
| 默认保留期 | 未开 ZDR 时通常保留 30 天用于滥用监控 |
| 境内 API | 不构成数据出境，但政策参差：DeepSeek 开放平台条款**对是否用于训练保持沉默**（与 OpenAI/Anthropic 明确承诺 API 数据不训练形成对比），需手动关闭"改进模型"设置 |
| 本地分发的额外问题 | 平台装在每个 TA 电脑上 → **API key 会分发到每台机器**。即使加密存储，也等于把公司密钥交给终端 |

**可接受的用法**：只送**不含候选人任何信息**的内容。典型是 **JD 原文结构化**——
JD 是公司自己的岗位描述，不是个人信息。

**不可接受**：把简历/候选人档案送 API。即使去掉姓名电话，"某 985 硕士 + 接口测试 3 年 +
苏州 + 香港城市大学"这样的组合仍可定位到人，在个保法下仍属个人信息。

## 三、分层落地方案（按建议顺序）

### 第 0 步（必做前置）：修掉现有的语义不同步
把 `setSemanticProvider` 在平台侧也接上，或者两边都暂时关掉。
**不修这个就往上加 AI，等于在歪地基上盖楼。**
成本：极小（平台侧几行代码）。收益：消除 14 分的无解分歧。

### 第 1 步：本地 embedding 接管语义层
- 用 bge-small-zh（约 100MB）替换现有的同义词表 + TF-IDF；
- 保留同义词表作为兜底与"领域强规则"（比如明确声明"金融≠电商"）；
- 平台侧与插件侧同时接入，用同一个模型、同一个版本号，并加入 `contract:check` 防漂移；
- 收益：解决"字面像、实质不同"的误判，这是当前评分翻车的核心。

### 第 2 步：JD 结构化助手（走云 API，只送 JD）
- 解决 v4 评分死在哪儿的问题：HR 填不出 `domain`/`tasks`；
- 输入只有 JD 原文，零候选人信息，合规风险可控；
- 建议用**境内**大模型 API + 企业协议 + 明确关闭训练用途；
- API key 不随安装包分发，改由平台从公司内部服务代取（避免密钥落到每台终端）。

### 第 3 步（可选，需政策审批）：简历结构化
只有在公司明确批准"候选人简历可送某个 API"之后才做。否则维持现状。

## 四、成本估算

| 项 | 估算 |
|---|---|
| 本地 embedding 模型体积 | 100MB（随安装包或首启下载一次） |
| 本地 embedding 推理 | CPU 毫秒级/条，评分场景（一次几十条）无感 |
| JD 结构化 API 成本 | 单次约 1500 token 输入 + 800 输出，按境内模型价格是可忽略的量级 |
| 工程量（第 0 步） | 极小 |
| 工程量（第 1 步） | 中等，难点在 Electron 打包原生模块 + 插件侧的落地形态 |
| 工程量（第 2 步） | 中等，含 UI、密钥管理、失败降级 |

## 五、关键风险与失效场景

1. **只接一边** → 把现有 14 分的不同步扩大。必须两边同时接，并有自动化闸门守着。
2. **embedding 不是万能**：它能判"语义近似"，但判不了"这个经验能否迁移到那个场景"。
   "金融风控"与"电商推荐"在向量空间里会很近——**这正是我们要区分的东西**。
   所以 embedding 必须与领域规则（domain/tasks 配置）配合，不能取代它。
3. **模型版本漂移**：两边模型版本不同 = 分数不同。要像现在守扩展 ID 一样守模型版本。
4. **首次下载失败**：TA 电脑网络受限时模型下不下来 → 必须有"没有语义能力也能工作"的降级路径
   （引擎本来就支持 `hasSemantic()` 为 false）。
5. **API key 分发到终端**：平台装在每个 TA 电脑上，key 就在每台机器上。必须避免直接内置。
